# Codegen caps

Differences that are **not source-fixable**. Each entry exists to stop an
investigation, not to start one.

When a residual diff matches an entry here, the reconstruction is already
correct. Commit it as a `FUNCTION` without `[MATCHED]`, add the address to
`caps-registry.tsv`, and move to the next target. Do not rewrite the source to
chase the percentage.

Read one section when the index in `codegen-index.md` points at it.

## [CAP-01] Address-taken pointer local forces spill and reload (locked vertex buffers)

- When a function locks a vertex buffer (or any out-param) and fills it field by field, retail MSVC6 **reloads the pointer from its stack slot before every store** (`mov reg,[esp+N]; mov [reg+off],val` per field). It never keeps the pointer in a register across stores.
- This happens because the pointer local is **address-taken**. Its address is passed to the lock API (`LockVertexBuffer(..., &ptr, ...)`). MSVC6 must spill an address-taken variable to memory because the callee writes through the pointer. Each subsequent `ptr[i].field` then reloads `ptr`.
- If you instead introduce a *separate* non-address-taken local (`Vertex* vertices = (Vertex*)lockedData;`) to clean up the cast, MSVC6 keeps `vertices` in a caller-saved register. It caches that register across stores. This drops the match substantially, even though the semantics are structurally identical.
- Fix: make the locked pointer itself the typed, address-taken local. Write `Vertex* lockedData; LockVertexBuffer(..., (LPVOID*)&lockedData, 0);`, then use `lockedData[i].field` directly. The `(LPVOID*)&` cast satisfies the `void**` out-param signature. It keeps the pointer address-taken, so MSVC spills and reloads it exactly like retail.
- A regalloc cascade like this can also shift the whole frame's stack scheduling (e.g. an apparent +4 stack-offset shift in a downstream section). Do not chase the offset independently. Fix the pointer spill first.

(`Vertex` here is a generic placeholder for the locked buffer's element type.)

## [CAP-02] char-in-`al` regalloc trap (do not chase it)

- In character-loop functions (functions that iterate over a string and switch on each `char`), retail tends to keep `char c` in `al` with `ecx` as switch scratch (`(uint8_t)c` = `and eax,0xff`). A reconstruction may spill `c` to a stack slot and use `eax` as scratch. This forces a default-case reload.
- This ripples through every iteration. It flips the `ebx`/`ebp` callee-saved assignment. Retail may also leave an else-branch `max(x,x)` compare unfolded.
- All of these are pure codegen differences with **identical semantics**. They can cap a correct function well below a match.
- The difference is not source-fixable without degrading contortions (volatile, address literals).
- Confirm the semantics. Keep the natural source. Record the mismatch. Move on. Do not burn a compare budget to nudge MSVC's register allocator.

## [CAP-03] Regalloc cascade from body length (ECX vs EDI for a pointer local)

- MSVC6 picks the register for a frequently-used pointer local (`Obj* o = g_current;`) by whole-function register *pressure*, not by the prologue.
- A short function keeps it in a caller-saved reg (`ECX`). Callee-saved saves (`push ebx/ebp/esi/edi`) defer past the null guards, with no `push ecx` frame slot.
- A longer function with the same prologue source evicts it to a callee-saved reg (`EDI`). This forces all callee-saved saves earlier (before the guards) and adds a `push ecx` slot. It shifts every scratch stack offset by 4 for the whole body.
- This is compiler-incidental and source-resistant. If you drop the pointer local and reference the global directly, it does not help. MSVC CSEs the repeated loads into the same callee-saved register anyway.
- When a sibling matches but a longer one with identical per-block logic does not, check whether retail's prologue uses a caller-saved register for the pointer local while yours uses a callee-saved one. If so, the gap is likely this cascade, not logic. Confirm it by isolating one block and verifying that it matches modulo `esp+0xN` offsets. Then accept the regalloc difference rather than contort the source.

## [CAP-04] Eager vs lazy callee-saved push (MSVC prologue inconsistency)

- For two near-identical functions that differ only in type constants and a log string (same body, different enum constants, different log text), MSVC6 may push a callee-saved register (`ESI`) **lazily** (after an underrun `je`, so the early-out path skips the push/pop) for one function but **eagerly** (at function entry, so the early-out path must `pop esi`) for its sibling.
- This cascades. The eager push shifts all parameter stack offsets by 4. It adds a `pop esi` to the early-out epilogue. So the diff looks structural, but it is pure prologue scheduling.
- This is not source-fixable. If you restructure the guard, add or remove `else`, or remove pointer casts, the eager push stays in place. One sibling can match fully with the identical source that falls short on the other.
- Accept the partial match. The success-path body matches instruction for instruction. Do not burn a compare budget to chase MSVC's register allocator across siblings.
- Single-function root-cause signal: when a `= 0`-initialized local is also the value that an early-out path returns, retail may zero a callee-saved register (`xor reg,reg; mov [local],reg`) and reuse that register for the early-out `return` (`mov eax,reg` at a far tail). This forces an **eager** push of that register because it is needed before the early-out test. A reconstruction that instead stores an immediate 0 (`mov [esp+N],0`) gets a **lazy** push after the early-out. It gets a near-tail `return 0` instead of a far `mov eax,reg` tail. It also gets a full `[esp+N]` offset cascade. Neither `return 0` nor `return <local>` triggers the register allocation in the reconstruction. It is not source-fixable. Confirm that the body matches modulo the offset shift. Accept it.

## [CAP-05] Running-pointer vs indexed regalloc (vertex copy / locked-VB loops)

- For a tight vertex-copy or offset loop that writes `dst[i].field = a + src[i].field`, MSVC6 favors **two running pointers** (e.g. EAX = src += stride, ECX = dst offset += stride, base reloaded into EDI each iteration, writes `[ecx+edi-N]`) over the natural indexed form `dst[i].field = a + src[i].field`. The indexed form compiles to a base+`eax*1` scaled-index address mode and a separate index counter.
- The running-pointer form reads the source via `[eax-N]` (a pre-incremented pointer). It writes the dest via `[ecx+edi-N]` (a running offset plus a base reloaded from the stack each iter). The indexed form reads `[edi+eax+N]` and writes `[ecx-N]`, with an `add ecx,stride`/`add eax,stride` pair anyway.
- Both are semantically identical. The diff is pure address-mode and regalloc selection. It is not cleanly source-fixable. `*ptr++` post-increment forces a *different* (worse) post-increment addressing. Explicit `BYTE*` running casts are contortions. The natural indexed `dst[i].field` form is the readable original source. Accept the partial match for vertex-copy leaves where retail clearly used running pointers.
- Signal: retail disasm shows `mov edi,[esp+N]` (base reload) inside the loop body alongside `add eax,stride`/`add ecx,stride` and `[reg+reg-N]` stores. That is the running-pointer form. It is not a missing optimization in yours.

## [CAP-06] Locked-VB write loops commonly cap on address-mode choices

- Functions that lock a vertex buffer, loop over a vertex count, and write or read fields in the locked buffer commonly cap well below a match with **structurally correct** bodies.
- Two persistent MSVC6 address-mode choices, neither cleanly source-fixable:
  1. **Running pointer vs indexed**: as above. Retail walks a running src pointer and a running dst offset with the locked base reloaded each iteration. The natural `dst[i].field = a + src[i].field` compiles to base+`eax*1` scaled-index instead. `*ptr++` post-increment is *worse*. Explicit `BYTE*` casts are contortions.
  2. **Diffuse field base offset**: for `dst[i].diffuse.{r,g,b}` access, retail bases at `&diffuse` (+0x10) and indexes +2/+1/+0. MSVC from `dst[i].diffuse.r/g/b` bases at +0x11 (g's offset) and indexes +1/+0/-1. This is a dead base-LEA shift. A `uint8_t* color = &dst[i].diffuse` byte-pointer form does **not** fix it (same +0x11 base).
- This also affects the saturating fixed-point clamp. Retail shares the store (`mov ecx,0xff`/`sar ecx` → common `mov [eax],cl`) with `jle` branch direction. A `uint8_t result` local makes MSVC share the store. But it still emits `or cl,0xff` (vs `mov ecx,0xff`) and `ja` (vs `jle`).
- The saturating multiply idiom itself is period-plausible fixed-point: `if ((product & 0xfffff000) <= 0xff000) byte = product >> 12; else byte = 0xff;` (12.4 fixed-point, 0x1000 = 1.0, clamp to 0xFF). Keep it. Do not replace it with `min()`/`<cmath>`.
- Accept the partial match for these locked-VB vertex loops. The success-path instructions all match modulo address-mode and regalloc. Do not grind the running-pointer wall. It is the same cap across the cluster.

## [CAP-07] MSVC6 load-before-store deferral in consecutive struct copies (regalloc)

- For two consecutive struct copies like `dst[0].pos = srcA; dst[1].pos = srcB;` (3-dword Vector3F copies), MSVC6 interleaves the source loads. But it may **defer the stores**. It loads a later field into a free register *before* it stores an earlier one. Then it stores the deferred field later. It may also load a field into a register and defer that store past unrelated stores (e.g. a diffuse or color store that uses a different reg).
- A clean source `dst[0].pos = srcA; dst[1].pos = srcB;` sometimes compiles to the *immediate-store* variant instead. It stores each field right after its load. This gives a partial match. The ONLY diff is typically: register choice for one deferred field, plus store timing (immediate vs deferred past an independent store). All loads and stores are semantically identical.
- Do **not** contort source to chase this. A local that forces an early load can make it far worse (it forces a stack spill). Field-by-field copy is also worse (it loses the nice interleaving). Accept the partial match as compiler-incidental for these small inline-vertex renderers. The structural model (vertex layout, field roles, call sequence) is fully confirmed.
- Signal: the diff shows a register-choice swap for one struct-copy field, plus 1-2 store-ordering swaps after a `push`. Nothing else differs. That is this pattern, not a data-model error.

## [CAP-08] Unsigned bounds-check `jbe` vs signed `jle` (toolchain-version artifact)

- Retail emits `cmp reg, N; jbe` (unsigned) for a bounds check like `if (idx > N) return err;` where the index is an unsigned slot or array index. Our MSVC6 toolchain emits `jle` (signed) for the *same* source, even when the parameter is declared `unsigned`/`uint32_t`.
- If you change the parameter type to unsigned, it does **not** reproduce retail's `jbe`. The difference is a toolchain-version or codegen artifact, not a source type issue. Do not churn the type (and risk call-site conversion warnings) to flip the opcode. It will not move.
- This cap is shared across a whole cluster of small bounds-checked accessors on the same array. A sibling accessor in the same file with an identical source pattern exhibits the same `jbe`/`jle` + folded-array-offset diff. Treat the cluster as uniformly capped rather than per-function.

## [CAP-09] Multi-loop buffer copy/present routines can compile FPO while retail uses an EBP frame (whole-frame regalloc cap)

- A lock-surface → several back-to-front copy+clear loops (running pointers, per-iteration pointer advance by pitch) → unlock routine may compile with FPO (`SUB ESP, N` only, no `PUSH EBP; MOV EBP,ESP`). It may keep all pointer locals in callee-saved registers. Retail may instead use an EBP frame with the pointer locals homed in stack slots (`[EBP-N]`) and **reloaded each outer loop iteration**.
- This is a toolchain-version regalloc decision. It is the same family as the "Regalloc cascade from body length" and "jbe vs jle" caps, but at the **whole-frame** level. Retail's MSVC6 spilled the pointers and adopted an EBP frame. The build's MSVC6 kept them in registers with FPO. It is **not source-fixable**. Tests showed that hoisting the pointer locals to function scope, adding shared count locals, or restructuring the loops did not flip the frame. The FPO-vs-EBP and register-vs-stack-homed choices are made by the back-end's pressure heuristic, not by the source shape.
- The result is a near-total mismatch (single-digit %) dominated by the frame difference. Every stack access shifts. `PUSH EBP`/`MOV EBP,ESP` is extra. The per-iteration pointer reloads are absent. This holds **even though every loop's logic is instruction-for-instruction correct**. Do not mistake this for a logic or type error. If you chase it, you burn the compare budget without progress.
- Signal: retail prologue is `PUSH EBP; MOV EBP,ESP; SUB ESP, <struct+locals>` with `MOV ESI/EDI, [EBP-N]` reloads inside the outer loop and `ADD [EBP-N], pitch` that advances the stack slot. The build is `SUB ESP, <struct>` (FPO) with the pointers held in ESI/EDI across the outer loop and advanced in-register. A sibling surface function (e.g. one that also locks a surface desc and calls the same lock/unlock helpers) may match fine with FPO. The EBP frame is specific to the higher-pressure function, not to the surface-desc pattern.
- When a present/copy routine shows this whole-frame cap, accept that it is not matchable from source. Move to a smaller leaf rather than rewrite. You can still record the logic as a correct (if low-match) reconstruction only if the frame difference is the sole diff. Otherwise prefer to leave the STUB.

## [CAP-10] Constant-count `rep stosd` count hoisted into ECX early caps field-zero functions (toolchain artifact)

- When a function combines a constant-count `memset`/zero-fill (which lowers to `rep stosd` with `ECX = <dword count>`) with other field zero-stores, the repo's MSVC6 **hoists `MOV ECX, <count>` to the top** of the function (before the field stores). This ties ECX up as the count register for the whole body. It forces the field-store zero value into EAX and the struct base into EDX.
- Retail's MSVC6 instead uses ECX for the field-store zero first (`XOR CL,CL` for byte stores, then `XOR ECX,ECX` for dword stores). It loads the count into ECX **late** (right before `rep stosd`). It keeps the struct base in EAX.
- The result: identical store structure (same offsets, widths, values, and coalesced dword/word/byte pattern) but every operand register differs (base EDX vs EAX, zero EAX vs ECX). This caps the function well below a match despite a fully-correct model.
- This is not source-fixable. The count is a genuine compile-time constant, so MSVC hoists it regardless of source form (memset, a for-loop of dwords, etc. all produce `rep stosd` with an early `MOV ECX,count`). If you restructure the field stores or change the zero-fill construct, it does not flip the scheduling.
- Confirm it via the build bytes. If `MOV ECX, <count>` appears near the top (before field stores) while retail has it right before `rep stosd`, this is the artifact. Accept the cap. Keep the natural source.
- Sub-structure note: for a partial byte-array zero (e.g. `arr[1..N-1]` with `arr[0]` preserved), a `for (i=1; i<N; i++) arr[i] = 0;` loop coalesces to the same dword/word/byte store pattern retail uses (addressed off the struct base). `memset(&arr[1], 0, N-1)` instead materializes a separate base pointer (`LEA reg, [base+off]`) and mismatches structurally. Prefer the loop for partial-array zeroing when retail addresses off the struct base.

## [CAP-11] Multiple address-taken out-params to one COM call can cap on slot coalescing (toolchain artifact)
- A function that passes several address-taken out-param locals to a single COM method (e.g. `IDirectSoundBuffer::Lock` with 4 out-params: two `LPVOID*` and two `LPDWORD`) can cap well below a match even with a fully-correct model. Retail's MSVC6 and the build's MSVC6 coalesce the out-params into dead argument slots **differently**, and reserve a different frame size.
- Retail tends to reserve a larger frame (`SUB ESP, 0xc` for 3 dwords) and coalesce three of the four out-params into the dead argument slots (the slots of args already moved to registers or consumed by the call), leaving one out-param in a fresh local. The build tends to reserve a minimal frame (`PUSH ECX` for 1 dword, the frame-slot trick) and coalesce the out-params into a different selection of slots, with one in the single fresh local.
- The discriminator is **not** the declaration order of the locals (reordering them does not change the coalescing). It is the toolchain version's register-pressure / slot-coalescing heuristic, the same family as the `jbe`/`jle` and body-length regalloc-cascade caps.
- Signal: the verbose compare shows the prologue `SUB ESP, 0xc` vs `PUSH ECX` mismatch, the four `LEA` out-param addresses resolving to different `[esp+N]` offsets, and every subsequent instruction (the memcpy `REP MOVSD`/`MOVSB` loops, the `Unlock` arg setup, the epilogue) matching instruction-for-instruction **modulo the `[esp+N]` offsets**. The offsets are not a constant shift (the slot assignment genuinely differs), which distinguishes this from a pure frame-size cascade.
- Do not chase it. The natural readable form (declare the out-params as locals in the method's parameter order, pass `&local` to the method) is the credible original source. Forcing a specific slot assignment would require casts that reuse parameter variables as out-params (`(void**)&param`), which is contortion and still does not reproduce retail's exact assignment because the coalescing heuristic differs. Accept the partial match. The semantic model is fully confirmed by the matching instruction tails.
- This generalizes the single-out-param gotcha ("Address-taken out-param local reuses a dead parameter's stack slot"), which matches cleanly. With one out-param the coalescing is deterministic. With several, the toolchain picks different slots than retail.

## [CAP-12] MSVC block-reordering places cold exiting blocks differently across toolchain versions (label order does not control it)

- A function with multiple exiting paths inside a loop or check (e.g. a `return <code>` or `goto label` from inside a loop body, where the target block always exits) has its cold exiting block placed by MSVC's block-layout heuristic. The build's MSVC version places the cold block near its source (right after the loop/check that reaches it), while retail places it at the far tail (after the fallthrough/success path). This is NOT controlled by the label declaration order in source.
- Concretely: for a `do { ...; if (cond) goto coldBlock; ...; } while (...); <fallthrough>`, retail lays out `[loop][fallthrough][other-cold][coldBlock]` (coldBlock at the far tail). The build lays out `[loop][coldBlock][fallthrough]` (coldBlock right after the loop, before the fallthrough). Swapping the label declaration order, or using an inline `return` vs a `goto label`, does not change the placement — both forms produce the same cold-block-near-source layout in the build.
- This is the same family as the "Inverted if (ok) places error returns at the far tail" and the if/else branch-layout gotchas, but it specifically concerns blocks reached by forward `goto`/`return` from inside a loop or mid-function check. The build's MSVC and retail's MSVC disagree on whether the cold exiting block goes near its source or at the far tail.
- Signal: the verbose compare shows the same instructions in each block, but the blocks are in a different order, and the conditional-branch displacements differ (near vs far jumps) accordingly. The instruction *content* matches modulo the block order.
- It is not cleanly source-fixable. Restructuring to move the cold block (e.g. a flag + `break` + post-loop `if`, or nesting the fallthrough in an `else`) does not reliably reproduce retail's far-tail placement, because the build's MSVC reorders by its own heuristic regardless. Accept the partial match. The semantic model is confirmed by the matching instruction tails within each block.
- A related peephole: on the success path, `return result;` where `result` is provably 0 (after `if (result != 0) goto cleanup;` or `if (result == 0) goto success;`) is optimized by the build's MSVC to `xor eax,eax`, while retail keeps `mov eax,esi` (the result register). This is the same toolchain-version peephole difference; it is not source-fixable without contortion. Both `return result;` and `return 0;` produce the `xor` in the build.

## [CAP-13] `do {} while` with a forward `goto`/`break` inverts to JAE+JMP (toolchain-version loop-compilation artifact)

- A `do { ...; if (cond) goto found; ...; } while (ptr < bound);` where `found:` is a labeled block placed AFTER the loop (but inside the enclosing `if`) compiles differently across MSVC toolchain versions.
- Retail's MSVC keeps the natural `do {} while` form: the condition test is at the bottom as `CMP ptr, bound; JL loop_top` (loop back if less). The `goto found` is a forward `JZ` that jumps to the found block after the loop. The no-match exit (fall-through from `JL` not taken) has its own epilogue (`POP; XOR; RET`). The found+clear path falls through to a shared epilogue at the function tail.
- The build's MSVC treats the forward `goto`/`break` as a loop break and inverts the loop: the condition becomes `CMP ptr, bound; JAE exit; JMP loop_top` (exit forward if >= bound, unconditional loop-back). It also merges the no-match and clear epilogues into one shared exit (the `JAE` target), so the no-match path loses its separate `POP` epilogue.
- Three source forms were tested — `break`, `goto end` (crossing the if-boundary), and `goto found` (forward within the if) — all produce the same `JAE+JMP` inversion. The inversion is triggered by ANY forward jump out of the `do {} while` body, regardless of the target's scope. It is not source-fixable.
- The MOV-scheduling hoisting (the build hoists the loop-pointer init before the guard `JE`; retail places it after) is a related minor scheduling difference in the same family.
- Signal: the verbose compare shows the loop-exit/no-match region differing (`JL` vs `JAE+JMP`, separate vs merged epilogue), while the found block, clear block, and all other instructions match instruction-for-instruction. The loop-bound `CMP` operand may also resolve to a different adjacent data symbol on the build side (the one-past-end pointer lands on a neighbor); this resolves as more functions match.
- Accept the partial match. The semantic model is confirmed by the matching found/clear blocks. Do not restructure the loop to chase the `JL` form — no source form reproduces it with a forward goto.

## [CAP-14] Pointer local from a table load: retail keeps it in ECX, our toolchain keeps it in EAX (EAX<->ECX swap, not source-fixable)
- When a function loads a pointer from a table (`MOV EAX,[table_sub]`), then uses it both to compute a cursor (`ptr + N`, stored) and to read 16-bit fields (`MOV AX,[ptr]`), retail and our MSVC6 toolchain pick **different** home registers for the pointer local. This is the `Regalloc cascade from body length` family specialized to a table-loaded pointer.
- **Retail** copies the pointer to ECX (`MOV ECX,EAX`), advances EAX for the cursor (`ADD EAX,N`), stores the cursor from EAX, then reuses EAX/AX for the 16-bit field loads (`MOV AX,[ECX]`). EAX is the "work" register (cursor + 16-bit fields); ECX holds the pointer.
- **Our toolchain** keeps the pointer in EAX (where the table load put it), computes the cursor via `LEA ECX,[EAX+N]`, stores it from ECX, and loads 16-bit fields into CX (`MOV CX,[EAX]`). ECX is the "work" register; EAX holds the pointer.
- The result is a function that matches instruction-for-instruction **modulo a global EAX<->ECX swap**. Every load, store, compare, and branch is semantically identical; only the register names differ. The score sits around 50-55% because the swap touches most of the body.
- It is **not source-fixable**. Six forms were tested on one such function (int16_t* with a field local; inline field reads; a named cursor local; byte-pointer arithmetic `(uint8_t*)ptr + N`; a struct-pointer with `header + 1`; `&sequenceData[3]` address-of). All produced the identical swap at the identical score. Our toolchain consistently keeps the table-loaded pointer in EAX and will not move it to ECX to free EAX/AX for 16-bit loads, regardless of source shape.
- The trigger for retail's choice is that it plans to use AX (the 16-bit accumulator) for the field loads, so it frees EAX by moving the pointer to ECX and reusing EAX for the cursor then the fields. Our toolchain plans to use CX for the 16-bit loads (no EAX conflict), so it leaves the pointer in EAX. The 16-bit-load register choice (AX vs CX) is the root, and it is a toolchain-version heuristic.
- Signal: the verbose compare shows a clean EAX<->ECX (and AX<->CX) swap across the whole cursor+field region, with the position stores and table lookup matching exactly before it. The `ADD EAX,N` (retail cursor) vs `LEA ECX,[EAX+N]` (ours) pair at the cursor is the tell.
- Accept the partial match. The semantic model is fully confirmed by the matching instruction tails (modulo the register names). Do not burn a compare budget trying to flip it. The function is a correct reconstruction; the low score is a toolchain regalloc artifact. Commit it as a `FUNCTION` (no `[MATCHED]`) and record the cap. If the function establishes shared globals (e.g. a table or peak-tracking state used by other not-yet-reconstructed functions), committing it is still net positive: the `// GLOBAL:` annotations register the retail address-to-name mappings that future reconstruction will resolve.
- A struct-pointer form (`Header* h = (Header*)table[idx]; cursor = (uint8_t*)(h + 1); h->field`) is the most readable source for this shape and reproduces the same swap. Prefer it over raw `int16_t*` indexing when the pointer dereferences a real multi-field header: it documents the layout without changing the codegen.

## [CAP-15] Struct field re-read from memory vs CSE into a register (16-bit `ADD AX,[mem]` vs 32-bit `ADD EAX,ECX`)
- When a function reads the same struct field (through a pointer) in two separate expressions — once for a subtraction/comparison and again for an add to write it back — retail MSVC6 **re-reads the field from memory** for the second access (`ADD AX, [obj+off]`, a 16-bit add straight from memory). Our toolchain instead **CSE's the earlier load** into a register and reuses it (`ADD EAX, ECX`, a 32-bit add from a register). The value is provably unchanged between the two reads (no intervening call or store), so the CSE is semantically valid. Retail simply does not do it.
- This is NOT the "read struct fields on demand" gotcha (that one is about avoiding named locals to prevent a frame-size cascade — the build spilling where retail kept values in registers). This is the inverse: retail re-reads from memory where the build keeps the value in a register. Do not add a local to "help"; the local is CSE'd the same way.
- It frequently co-occurs with a **scratch-register pre-load in a scheduling gap**: retail copies a shared operand (e.g. a delta reused by a later IMUL) into EDX during a free gap between two earlier stores (`MOV EDX, EBX`), because it keeps the accumulator live across a branch and cannot reuse it for the later product. Our toolchain stores the accumulator earlier, frees it, and loads the shared operand into EAX at the use site. That single scheduling choice cascades through the whole region (which register holds the product, which register holds the next field read, 16-bit vs 32-bit adds, store timing before/after a TEST).
- A clean struct-of-positions/angles smoothing or lerp function (`obj->f += (obj->g - obj->f) >> k;` then angle wrap with `if (delta >= 0x800) delta -= 0x1000;` and `obj->f = (obj->f + (delta >> m)) & 0xfff;`) is the textbook shape that triggers it. The position/lerp half of such a function matched 100%; only the angle-wrap region shows the cascade (~75% match).
- Not source-fixable. Tested: a named local for the first field read, deferring the field writeback past the branch, and hoisting the squared product out of the if/else — the last one actively regressed (it broke the branch layout; the branch-body duplication of the squared product is REQUIRED for the correct layout, and the if/else form reproduces the `TEST; JGE` + duplicated-IMUL block structure exactly). Writing the negated-angle delta as a separate `angle = -angle;` statement DID fix the `NEG; SUB` vs `ADD; NEG` order (MSVC algebraically folds `(-a - b)` into `-(a + b)`; splitting the negate prevents the fold).
- Signal: the verbose compare shows the position/lerp prefix matching exactly, then an angle region where retail has `ADD AX, [obj+off]` and a mid-sequence `MOV EDX, EBX` while the build has `ADD EAX, ECX` and a later `MOV EAX, EBX`, with every other instruction matching modulo register names. Accept the partial match. The function is a correct reconstruction; commit it as a `FUNCTION` (no `[MATCHED]`). If it also establishes a shared struct used by a whole cluster of not-yet-reconstructed functions, the struct definition is the real value.

## [CAP-16] Retail unrolls a small constant-count struct-copy loop; our toolchain keeps it a counted loop

## [CAP-17] Loop-invariant `x - const` init hoisted early as LEA vs retail's late MOV+SUB (count register pressure)
